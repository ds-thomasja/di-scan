h2. User Story

As a clinical user, I want a selectable card representing a single scan-catalog entry – with clear states, so that I can select and remove individual scan catalogs within a catalog list.

h2. Acceptance Criteria
 - *Functional:*
 -- Tapping the card (when not {{{}disabled{}}}) calls {{{}onTap{}}}, then flips the internal selected state and calls {{onSelectedChanged}} with the new value.
 -- {{selected}} only seeds the *initial* layout; subsequent external changes to {{selected}} are re-synced via {{didUpdateWidget}} (so a host that owns selection externally, like {{{}CatalogList{}}}, can still drive the card after the first build).
 -- When {{{}isDragTarget{}}}, the label always shows the fixed text "Switch" (colour {{{}text.interactive{}}}) regardless of {{{}name{}}}, and {{subtext}} is force-hidden even if {{showSubtext}} is {{{}true{}}}.
 -- When {{{}isDragSource{}}}, {{{}name{}}}/{{{}subtext{}}} render using {{{}name{}}}/{{{}subtext{}}} verbatim but always in {{text.disabled}} colour, regardless of {{selected}} — *this was a same-day fix; previously the placeholder used {{text.standard}} when the dragged item happened to be selected, which is now overridden unconditionally.*
 -- The status icon and the "Remove catalog" overflow menu are both suppressed whenever {{isDragSource}} or {{isDragTarget}} is true (`&& !widget.isDragSource && !widget.isDragTarget` / `&& !widget.isDragSource` guards) — *also a same-day fix; the placeholder previously still rendered its remove button and, if {{{}showStatus{}}}, its status icon, neither of which appear in the Figma Placeholder node (4750:15781 / 4750:15794).*
 -- A card the user is hovering the overflow-menu button on does not trigger the whole-card press-scale animation ({{{}_isButtonHovered{}}} guard), even while the pointer is technically down on the card.

 - *States:*
 -- Default: {{surface.standard}} background, 1 px {{border.subdued}} border (compact) or no border (expanded, since the compact card's border is drawn via {{Border.all}} only when {{{}!_selected{}}}).
 -- Hover (not disabled, not pressed via the overflow button): {{surface.hovered}} background.
 -- Pressed (not via the overflow button): {{surface.pressed}} background, card scales to {{0.97}} over {{80 ms}} (ease-in-cubic in, {{300 ms}} ease-out on release).
 -- Focus: {{surface.standard}} background with a {{2 px}} {{border.focused}} border (overrides the default subdued border while focused).
 -- Disabled: background stays {{{}surface.standard{}}}; text renders {{{}text.disabled{}}}; icon renders {{{}icon.disabled{}}}; in the *expanded, with-scan-model* layout the whole image area additionally renders at {{opacities.disabled}} (0.4) via an {{Opacity}} wrapper. *Not independently re-verified against Figma for the expanded, without-scan-model (plain arch-icon) disabled variant — the implementation only changes the icon's colour there (no 0.4 group-opacity wrapper), by analogy with the compact disabled variant; flag for visual confirmation against Figma node 2290:3630 if that combination is exercised.*
 -- Selected (not dragging): expanded layout, plus a 2 px {{border.interactiveHovered}} border drawn as a separate overlay on top of the card.
 -- Drag source: {{surface.subdued}} background, transparent base border with a 2 px dashed {{border.standard}} overlay; image area empty (expanded) or an {{archUpper}} icon in {{icon.disabled}} (compact); text {{{}text.disabled{}}}; status icon and remove-menu both hidden; *dashed-border layout is now always {{Positioned.fill}} (unconditional) — a {{{}dragHasTarget{}}}-driven inset/extended-border toggle that previously existed was removed same-day on explicit user feedback that the placeholder should look identical regardless of whether another card is currently a valid drop target elsewhere in the list.*
 -- Drag target: {{surface.dropzone}} background, transparent base border with a {{2 px}} dashed {{border.interactive}} overlay (now always {{{}border.width.dropzone{}}}, 2 px, regardless of {{selected}} — a same-day fix; previously the non-selected/compact target used {{{}border.width.standard{}}}, 1 px); thumbnail/image replaced by a {{repeat}} icon in {{{}icon.interactive{}}}; label forced to "Switch"; subtext, status icon, and remove-menu all hidden.
 -- Loading: thumbnail/image slot replaced by an indeterminate {{{}DSProgressCircle.medium(){}}}; all other content (name/subtext/status/remove-menu) renders as in the card's non-drag state.

h2. Content Logic & Edge Cases
 - *Long name/subtext:* both truncate to a single line with an ellipsis (confirmed against the Figma "Text overflow" anatomy examples, e.g. node 4304:14419) — no wrapping, no tooltip-on-truncate.
 - *Text column height stability:* the name/subtext block uses an invisible height-reserving {{Column}} (both lines, {{{}Opacity: 0.0{}}}) underneath the real, positioned content, so the visible name centers vertically in a fixed-height block whether or not {{{}subtext{}}}/{{{}showSubtext{}}} is actually rendered — prevents row height from jumping based on subtext visibility.
 - *{{scanModel: true}} with {{{}scanModelImage: null{}}}:* falls back to the plain icon placeholder in both layouts.
 - *Mutually exclusive drag flags:* {{{}isDragSource{}}}, {{{}isDragTarget{}}}, and {{isLoading}} are not mutually exclusive by type (all are independent {{bool}}s), but the owning {{CatalogList}} only ever sets one of {{{}isDragSource{}}}/{{{}isDragTarget{}}} at a time per card, and only sets {{isLoading}} after both drag flags have cleared — *this contract is enforced by the caller, not by {{CatalogCard}} itself; passing an unexpected combination (e.g. {{isDragSource: true}} and {{isLoading: true}} simultaneously) is undefined visually since {{{}_compactImage{}}}/{{{}_expandedImage{}}} check {{isLoading}} first, then {{{}isDragTarget{}}}, then {{isDragSource}} in that priority order.*
 - *Status icon suppressed on all drag-related states, overriding raw Figma:* the Figma "Moving ..." floating-copy node (4750:15752) itself shows the status icon with {{{}status: true{}}}, but the user has explicitly decided the green status checkmark must never appear on any drag-related visual anywhere in the list (source, target, or the floating copy owned by {{{}CatalogList{}}}) — treat this as a standing rule over the raw Figma export if the two ever conflict again.
 - *Disabled cards are never draggable:* enforced by the caller ({{{}CatalogList{}}} passes {{null}} for {{onLongPressStart}} when an item is {{{}disabled{}}}), not by {{CatalogCard}} itself — {{CatalogCard}} has no awareness of drag gestures at all.
 - *Remove action is destructive-styled but not confirmed with a dialog:* {{DSAction(destructive: true)}} only affects the menu item's visual styling (per the DS {{DSActionsButton}} contract); triggering it calls {{onRemovePressed}} immediately with no intermediate confirmation step inside this component — *if a confirmation step is required by product, it must be added by the caller around {{{}onRemovePressed{}}}.*
 - *Same-day Figma drag-and-drop reconciliation (2026-09-15, not yet committed):* summarized in Acceptance Criteria/States above — placeholder text always disabled-styled regardless of selection, placeholder's remove-button/status-icon suppressed, drop-target border width unified to {{dropzone}} (2 px) regardless of selection, and the {{{}dragHasTarget{}}}-driven placeholder border-shape toggle removed entirely.
